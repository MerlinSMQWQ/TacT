# Verification for the TacT source repository

This supplements `core/verification.md` when working on the Kit and its initialization CLI. The core guidance about failures, evidence reuse, required checks, and truthful reporting remains applicable.

For an instruction migration, check that the intended files and local links resolve, the English-only guidance requirement is met (except for the original-language exchanges in `core/communication-examples.md` and the literal Chinese expressions in the wording-restrictions section of `core/communication.md`), and reasons, conditions, counterexamples, and boundaries survive the move. Compare against the preserved baseline. For conversation examples, compare the questions, answers, tool-activity records, and attached review against the supplied originals, allowing only Markdown transport unescaping and the surrounding example labels. For the wording restriction, compare the 50 distinct expressions with the two supplied images, check the two separately reported correction preambles, preserve the existing examples, and check that the explanation retains concrete uncertainty and evidence requirements. Inspect the actual host input and file-reading path for the selected adoption mode, then use a real task judgment to check application. File counts and a reading self-report alone do not establish adoption.

For CLI changes, run the relevant initialization and update tests, especially preservation of existing guidance, conflict handling, repeat operations, and dry-run behavior. Update checks should cover migration from an older installation, edited project notes, invalid manifests, and recovery after an interrupted write. For packaging or bundled-content changes, build both the source distribution and wheel and exercise an installed package outside the source checkout. Verify that shared guidance is included while this repository's project-specific constraints are excluded.

CLI tests establish file behavior, not agent adoption. Keep the distinction between startup discovery, explicit file acquisition, and observed task behavior in the reported result.

For root-entry updates, check new initialization, restoration of missing or empty root entries, and migration of a file consisting only of either known generated legacy entry, including dry-run and newline preservation. Check that project text, custom blocks, and formatting changes leave the entire root file unchanged while shared Kit updates complete. Retain checks for shared-file conflicts and recovery after interrupted refresh. The maintainer's Pi check should start a new session with only a short factual question and verify that communication guidance, required conversation examples, and any project supplement are obtained in full before the answer, or that their complete current contents were already supplied by the host. Inspect actual delivered output for both per-call and combined truncation, and check that subsequent reads cover every gap and partial line. A successful command or a reading self-report does not establish complete delivery.

For this iteration, the maintainer leads acceptance in Pi. Record the Pi version, model and configuration, trial project starting commit, and TacT candidate commit. Check separately whether Pi discovers the entry, whether the agent actually reads `.tact/AGENTS.md`, `.tact/project/notes.md`, and the triggered topic files and matching project supplements, and whether observed decisions and communication apply the guidance. Use session or event records and actual outcomes; a loading self-report or a mention of a rule is insufficient. Codex loading results do not substitute for Pi verification.

After substantive revisions to shared guidance, repeat the local checks affected by the change. If the revision changes collaboration behavior, also verify the affected scenario with a short task in Pi; a full repeat of the refactoring experiment is unnecessary. This applies to final consolidation as well as trial feedback. Reuse evidence that remains valid, and mark rules whose scenarios were not encountered or whose effects lack evidence without treating them as verified improvements. Completion of stages 0–2 leaves these Pi checks pending for the maintainer-led trial.
